## 1. 架构设计与安全性总体评价

- **内存模型**: 基于 `std.heap.ArenaAllocator`，程序生命周期内单次批量分配，退出时统一归还系统，无内存碎片、无悬垂指针泄漏风险。
- **C-ABI 交互**: 采用轻量 extern C 声明直通系统的 `libsqlite3.so`，彻底摆脱外部 C 头文件依赖，兼具纯粹性与极致启动速度。
- **安全性评估**:
  - ✅ 无命令注入风险（全原生系统调用，不调用 shell）
  - ✅ 无 SQL 注入风险（硬编码静态只读查询）
  - ✅ UTF-8 字符安全：使用 `std.unicode.utf8ByteSequenceLength` 逐 codepoint 截断，杜绝汉字断字乱码。

## 2. 缺陷审查与修复验证结果

### 缺陷 1 (P0): SQLite Handle 释放与空指针风险
- **原始问题**: `sqlite3_open_v2` 即使打开失败也可能分配 handle，官方规范要求必须显式 close；且 `db_ptr.?` 强制解引用存在 panic 隐患。
- **修复措施**: 引入 `if (db_ptr) |db| { defer _ = sqlite3_close(db); ... }`，确保任何分支安全释放。
- **验证结果**: **PASS**。测试损坏数据库与空数据库均安全跳过，无资源泄漏。

### 缺陷 2 (P0): 32KiB 跨 Chunk 边界匹配假阴性
- **原始问题**: 单块 32KiB 缓冲区分片读取时，横跨接缝边界的关键词会被截断漏检。
- **修复措施**: 引入 `overlap_len = kw.len - 1` 滑动窗口重叠，将上一个 chunk 末尾字节复制到下一个 chunk 开头，无缝拼接。
- **对抗性测试**:
  - `EXACTBOUNDARYKW` (起点恰在 32768 边界): **100% 命中**
  - `SPANTWOCHUNKSKW` (横跨 65536 两个 chunk): **100% 命中**
  - `ENDSATBOUNDARY` (末尾恰在 32768 边界): **100% 命中**
- **验证结果**: **PASS**（经由 CodeBuddy 构造极端合成用例严格验证通过）。

### 缺陷 3 (P0 安全防御): 超大关键词边界缓冲区溢出
- **审查发现**: 当搜索词 `kw.len >= buf.len`（如攻击者传入 40KB ~ 100KB payload）时，`kw.len - 1` 超出单块缓冲区长度。
- **修复措施**: 在函数入口增加强类型守卫：`if (kw.len >= buf.len or kw.len == 0) return false;`。
- **验证结果**: **PASS**。实测 40KB 与 100KB 超大关键词 Fuzz 搜索耗时 < 1ms，安全退出，零崩溃。

### 缺陷 4 (P1): CLI 参数解析顺序
- **原始问题**: 未知参数分支排在 `-h/--help` 之前，导致异常参数误触发帮助逻辑。
- **修复措施**: 显式重构参数分支，未知参数明确报错并退出。
- **验证结果**: **PASS**。
